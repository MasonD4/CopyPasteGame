The movement system
- - Right now I'm thinking that the movement system (for moving pieces one space orthogonally)
- - should be simpler than I'm making it. Here is how I think it can cleanly go:
- - - - You have a list of all of the widgets moving in a particular direction.
- - - - You have a function that parses through this list in whichever order it needs to.
- - - - - - This function will look at each widget/widget token/action token and plug it into
- - - - - - A function called `attemptMove()`, which takes in a widget token and a direction.
- - - - attemptMove()'s job is to simply check if a move is possible. If so, it calls another function,
- - - - - - `performMove()`. Here is how attemptMove() roughly works:
- - - - - - It checks if the current widget can move, if its position is valid, and other such stuff.
- - - - - - Then, it checks if the ending position is on the map. If so,
- - - - - - It checks if the widget in the ending position is air or can be stepped on. If so,
- - - - - - - - it calls performMove(), and passes in the action token and the direction.
- - - - - - If not, it checks if the widget in the ending position can be pushed. If so,
- - - - - - - - it calls another function, `attemptPush()` on that pushable widget. attemptPush()
- - - - - - - - is just like attemptMove(), except it has an extra integer parament used to ensure
- - - - - - - - the push limit isn't exceeded.
- - - - - - After calling attemptPush(), it checks if the ending position can be moved to now.
- - - - - - - - If so, it calls performMove().
- - - - - - - - If not, it checks any other conditions, if necessary. If they all fail, then the ending
- - - - - - - - position is either invalid or obstructed by something immovable. 
- - performMove() would be really simple:
- - - - It checks the direction and changes one of the spaces adjacent to the moving widget to
- - - - that widget. Then, it turns the widget in the original space to air.
- - - - Then, it calls xStepsOnYInteraction(), or whatever that's called.
- - 
- - The reason I thought of it is because I think bash will follow a similar pattern.
- - You call `` on whichever widgets you need to.
- - Within attemptBash(), it checks if there is a valid wdget to bash. If so, it calls
- - `` (which pretty much replaces the bashing widget with air and the bashed widget
- - with the bashing widget). If not, it simply calls off the bash. 
- - Note: if I decide that I want the bash action to be seperated based on direction, then the
- - direction of the bash should be chosen earlier in the pipeline than attemptBash(). this is because
- - attemptBash() assumes the specifics of the bash have already been figured out. It's only job is
- - to check if that specific bash is possible. If so, it calls performBash() and passes in
- - the token or whatever. If not, it simply quits.
- - It's possible that attemptBash() and attemptMove() will return a bool, in order to directly
- - report whether or not it was successful.
- -
- - Basically, actions such as move and bash should follow a clean and modular pipeline.
- - (using the move action as an example):
- - * The first step(s) of the pipeline, whatever they may be, aim to figure out:
- - - - * What's moving (if there are multiple widgets moving, it picks an order and sends them
- - - - - - through the pipeline one-by-one).
- - - - * Where it's moving from.
- - - - * What location/direction it's moving to.
- - * The next step is to call attemptMove(). It assumes that the details of the move have been
- - - - figured out. It's job is to find out if, given the details, that move can be executed. 
- - * The last step is to call performMove(). performMove() doesn't ask questions. It assumes that
- - - - the details are correct and the move is valid. It's job is to actually edit the map so as to
- - - - fulfill the move (and call xStepsOnYInteraction()). It should be just a few lines of code.

chronolog Feb 7 2026: Redoing the action token system.
Saturday February 7 2026
- - Today, while thinking of how to implement the rook, I realized that the system I thought up
- - has a major flaw.
- - For context, the system I am talking about is a system I devised to handle the game's
- - "order of operations". How it works:
- - - - * Scan through the entire map and look at each widget.
- - - - * If that widget wants to go somewhere or do something, create an action token for it and
- - - - - - push the token onto a vector of similar move token types.
- - - - * Once that is done, there should now be a few vectors, each containing a set of action
- - - - - - tokens that correspond to that vector. For example, the MoveWidgetUp vector should
- - - - - - contain a/a few MoveWidgetUp action token(s) (assuming there are any widgets wanting to
- - - - - - move upwards).
- - - - * Loop through each vector, executing each action token.
- - So what's the flaw? Well, it is possible for actions to interfere with action tokens of
- - different types.
- - For example, let's say that there is a widget that wants to move to the
- - right. Let's say that there is also a rook targeting that widget. Let's say that the rook
- - gets to bash the widget before the widget gets to move. Here's what happens:
- - - - * The rook bashes the widget, thus destroying said widget and taking its place.
- - - - * Now it's the widget's turn to move. However, the widget doesn't exist anymore;
- - - - - - the rook is in its place.
- - - - * But the move token doesn't care. It only cares about looking at the position it was
- - - - - - told to look at, and then moving whatever is there.
- - - - * The rook is there, so the rook moves to the right.
- - - - * This is not something I want.
- - 
- - Perhaps each action token will have an "update" function that recalculates certain info.
- - Like for example, with a move token, think of this:
- - - - * There is a widget, and it is planning to move up, so it has a MoveWidgetUp token.
- - - - * However, the widget gets pushed to a new spot before it can execute its move token.
- - - - * For this reason, we want it to update its move token to reflect its new position.
- - - - * To do this, we call that widget's move token's update function, and pass in the widget's
- - - - - - new coordinates.
- - - - * The function will then use those coordinates to update the move token's starting
- - - - - - coordinates.
- - - - * Then, it will use the updated starting coordinates to calculate the new ending coordinates.
- - Perhaps it can also have a "destroy" function (or a destructor), in case thw widget that
- - corresponds to that token gets destroyed.
- - Or perhaps, instead of a destroy function, the token just gets pulled from the vector.
- - 
- - Something to consider: Maybe action tokens only need to be updated if they get pushed or touched
- - or otherwise interacted with by another widget.
- - 
- - Maybe each action token will include the coordinates belonging to the widget performing the
- - action (I think this is already the case). And maybe let's say that the only reason why 
- - that token would need to be updated is if the widget it belongs to:
- - * Gets moved
- - * Gets destroyed
- - * Gets turned into another widget type.
- - In other words, maybe as long as a widget doesn't get moved, destroyed, or changed, then no
- - matter what happens around it, it should still be allowed to attempt the action it's attempting.
- - And so, whenever a widget is performing an action that has the potential to move, destroy, or
- - change another, it will check to see if there are any pending action tokens that belong to a
- - widget in that location. If so, it will update that move token.
- -
- - For example, if a wdiget is moving up, it will check the spot above it to see if
- - there is anything other than air up there. If so, it checks if that space corresponds to
- - an action token. If so, and if the original widget is successfully able to move up
- - (which results in the widget above it getting pushed), it will update the other move token.
- -
- - Right now, to my knowldege, there are two types of actions that a widget can perform:
- - * Move/push
- - * Step on another widget
- - * I don't know if incrementing a counter is technically an action, but maybe that.
